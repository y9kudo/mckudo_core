# KudoVectorize · объёмная навигация

Автор **y9kudo**. KudoVectorize работает с наблюдаемой геометрией: проверяет тело, а не только луч между координатами. В 0.7-dev реализован водный A* с 26 направлениями, включая вертикальные и объёмные диагонали.

```js
import {KudoVectorize} from 'kudoconnect/vectorize';

const vector=new KudoVectorize({
  getBlock:p=>client.world.blockAt(p),
  getRevision:()=>client.world.revision
});
const route=await vector.planAsync({
  start:client.state.position, goal:{x:12,y:62,z:9},
  airTicks:300,airReserveTicks:60,maxNodes:6000,maxDistance:64
});
console.log(route.status,route.reason,route.waypoints);
```

`client` — уже подключённый KudoConnect. При собственной реализации `getBlock` возвращает блок с `name`, `shapes` и свойствами либо `null` для неизвестного мира. `null` не считается воздухом. `getRevision` позволяет отменить результат, если чанки изменились во время расчёта.

## Как проверяется путь

- Тело занимает 0,6 × 1,8 блока. Частичные формы заборов, плит и других блоков проверяются по collision shapes. Поза быстрого плавания высотой 0,6 блока пока не используется.
- Между узлами проверяется весь перемещаемый объём с шагом до 0,15 блока, поэтому диагональ не проходит сквозь угол стены.
- Лава, огонь, кактус и другие известные опасности запрещены. Водонаполненный твёрдый блок продолжает иметь коллизию.
- В воздухе нужны наблюдаемая опора и свободное тело. Водный планировщик не превращает агента в летающего игрока.
- Воздух списывается консервативно за подводные участки. Пополнение учитывается только на полностью надводном участке. `waterBreathing: true` разрешено задавать только при подтверждённом действии соответствующего эффекта; исполнитель автоматически это не предполагает.
- Поиск ограничен узлами/дистанцией; асинхронная версия уступает цикл событий по временному бюджету. Она возвращает `world-changed`, если мир изменился, вместо использования устаревшего пути.

Причины отказа: `invalid-start`, `air-budget`, `unloaded`, `no-route`, `search-budget`, `distance-budget`, `world-changed`. Это данные для перепланирования, а не успешное достижение цели.

## Исполнение

```js
await client.execute({skill:'swim',args:{x:12,y:62,z:9}});
```

Исполнитель использует обычные горизонтальные команды, подъём и приседание для погружения; повторно проверяет проход и серверный `air_supply`. Прямая запись нужной позиции вместо перемещения не используется. При отмене управление освобождается. У MCKudo есть `agent.swimTo(position)` и JSON `{ "swim": { "x":12,"y":62,"z":9 } }`.

Запас воздуха оценивается консервативно, но течение, урон и изменение блоков могут потребовать нового плана. Результат действия содержит достигнутую локальную позицию; отдельного серверного пакета «прибытие» Minecraft не присылает.

## Элитры

```js
import {predictElytraTick} from 'kudoconnect/vectorize';
const next=predictElytraTick({
  position:{x:0,y:100,z:0},velocity:{x:0,y:0,z:1},
  yaw:0,pitch:-10,rocket:true
});
```

Скорость задаётся в блоках за игровой тик; углы — в градусах. Это математическое предсказание подъёмной силы, сопротивления, поворота скорости и одного тика ускорения ракеты. `rocket: true` не расходует предмет и не отправляет пакет. Отслеживание раскрытых элитр, длительности ракеты, посадки и серверных коррекций ещё нужно связать с игровым исполнителем; автопилот не объявлен готовым. Для проверки объёма будущего полёта можно использовать `traceVolume` с соответствующей высотой тела.

Базовый контракт физики сверялся с [API сущностей Yarn 1.21.1](https://maven.fabricmc.net/docs/yarn-1.21.1%2Bbuild.3/net/minecraft/entity/LivingEntity.html). Точные численные параметры предиктора пока проверены модульными тестами, а не измерением полёта на сервере.
